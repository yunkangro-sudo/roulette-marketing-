## 2. v2.1 아키텍처 결정 5건

v2.0에서 미결이었던 5개 질문에 대해 아래와 같이 결정했다. 구현 시 이 결정을 기준으로 삼는다.

### 결정 A — activity_log vs daily_participation_log 이중 기록

**결정**: 두 테이블을 **역할 분리**한다. 이중 기록 허용, 실패 전략은 silent fail.

```
daily_participation_log  →  하루 1회 참여 제한 체크 전용 (게임 진행 여부 결정)
activity_log             →  분석용 행동 로그 전용 (게임 결과에 영향 없음)

이중 쓰기 실패 처리:
- daily_participation_log 쓰기 실패 → 게임 진행 자체가 막힘 (기존 로직 그대로)
- activity_log 쓰기 실패 → 에러 로그만 남기고 게임은 정상 진행 (silent fail)
```

**이유**: 두 테이블의 목적이 다르다. 통합하면 "분석 로그 실패"가 "참여 제한 체크 실패"와 뒤섞여 장애 범위가 커진다. 역할을 분리하면 하나가 실패해도 다른 기능에 영향이 없다.

---

### 결정 B — mission_progress.current_value 업데이트 타이밍

**결정**: **게임 완료 API(`/api/games/play`)에서 실시간 업데이트**한다.

```
게임 완료 API 호출 흐름:
1. 추첨 결과 계산 (기존)
2. coupons row 생성 (기존)
3. activity_log에 game_complete 기록 (신규, silent fail)
4. 해당 고객의 mission_progress.current_value += 1 (신규, silent fail)
5. 결과 반환

mission_progress 업데이트 실패 → 에러 로그 + 게임 결과는 정상 반환
(미션 진행률이 1회 누락되는 건 용인 가능한 수준, 게임 자체 실패보다 낫다)
```

**이유**: 배치(Cron)를 사용하면 Vercel Cron Job 추가 비용이 생기고, 현재 프로젝트에 배치 인프라가 없다. 조회 시점 계산(SELECT COUNT)은 고객이 많아질수록 느려진다. API 내 실시간 업데이트가 가장 저비용이고 Next Visit Loop 화면에서 즉시 반영된다.

---

### 결정 C — customer_loyalty.segment 재계산 타이밍

**결정**: **방문(게임 완료) 시점에 해당 고객 1명만 즉시 재계산**한다.

```
게임 완료 API 추가 처리 (결정 B 이후):
5. customer_loyalty.segment 재계산 및 UPDATE (신규, silent fail)

재계산 로직:
- 방문 횟수 1회 → NEW
- 방문 횟수 2회 이상 → 개인 평균주기 계산
  - 최근 30일 내 재방문 → ACTIVE
  - 개인 평균주기 × 1.5 초과 → AT_RISK
  - 개인 평균주기 × 3.0 초과 → DORMANT
  (이 시점에 게임 참여했으면 → DORMANT→RETURNED 처리 후 ACTIVE로)
```

**이유**: 전체 고객 배치(일 1회)는 배치 인프라 필요 + 지연 발생. 조회 시점 계산은 대시보드 조회마다 비쌈. "방문 시점에 해당 고객만" 업데이트는 인프라 추가 없이 구현 가능하고, 단 1명의 계산이라 성능 문제 없다.

---

### 결정 D — message_consent 초기값 및 동의 수집 방식

**결정**: **카카오 채널 친구추가 완료 = 마케팅 메시지 동의**로 간주한다.

```
message_consent 레코드 생성 시점:
- 카카오 채널 친구추가 완료 콜백 → consented = true로 INSERT
- 친구추가 미완료 손님 → 레코드 없음 = 발송 금지 (NULL-safe 처리)

발송 전 체크:
IF message_consent 레코드 없음 → 발송 안 함
IF consented = false → 발송 안 함
IF consented = true → 빈도 체크 후 발송

법적 근거: 카카오 채널 친구추가는 카카오 약관상 채널 메시지 수신에 동의하는 행위다.
별도 체크박스 불필요. 단, 수신거부(친구삭제) 시 consented = false로 업데이트하는
웹훅 처리가 향후 카카오 연동 단계에서 필요하다.
```

**이유**: 게임 화면에 동의 체크박스를 추가하면 UX가 복잡해지고 참여율이 떨어진다. 카카오 채널 친구추가 자체가 법적 동의 행위이므로 별도 UI 불필요. 카카오 연동(7단계) 전까지는 mockLogin 환경이라 message_consent 레코드가 생성되지 않아 알림톡 발송 자체가 차단된다(의도된 동작).

---

### 결정 E — milestone_rules 테이블 DB 존재 여부

**결정**: **milestone_rules는 DB에 없다. missions 테이블을 신규 생성한다.**

SQL 마이그레이션 파일 001~007 전체를 확인한 결과 milestone_rules 생성 구문이 없다. 설계도에만 언급되어 있던 "예정" 테이블이다. 따라서 마이그레이션이 아닌 신규 생성이며, 데이터 이전 작업 없이 바로 missions 테이블을 만들면 된다.

## 3. 채택 항목 상세 설계 (v2.1 확정판)

### 3.1 Next Visit Loop (신규채택)

**목적**: 보상 화면에서 "받았다"로 끝내지 않고 "다음에 왜 와야 하는지"를 항상 같이 보여준다.

**구현 방식**: 새 테이블 불필요. 기존 결과공개 화면(설계도 2절 ⑦)에 아래 정보를 조회해서 함께 노출한다.
- 현재 포인트 잔액 및 사용 임계값까지 남은 금액
- 진행 중인 미션이 있으면 그 진행률 (결정 B에 의해 실시간 반영)
- 다음 미션/등급까지 남은 조건

**우선순위**: 화면 문구/조회 로직 추가 수준이라 비용 낮음. 8-8 단계에서 구현.

---

### 3.2 방문 이벤트 구분 (신규채택)

**결정 A에 따른 역할 정의**:
- `daily_participation_log`: 하루 1회 참여 제한 체크 전용. 분석 목적으로 사용하지 않는다.
- `activity_log`: 분석·행동 추적 전용. 게임 진행 여부에 영향 없다.

**신규 테이블**:
```sql
activity_log (경량 행동 로그, 향후 분석용 원천 데이터)
- id           uuid      primary key
- store_id     text      not null
- kakao_user_id text     not null
- event_type   text      not null
  -- 실제 기록: game_start / game_complete / coupon_used / reward_redeemed / point_earned
  -- 타입만 예약(로직 없음): visit_checkin / purchase
- ref_id       uuid      nullable  -- coupon_id 또는 미션id 등
- occurred_at  timestamptz not null default now()
```

**체크 제약**:
```sql
check (event_type in (
  'game_start', 'game_complete', 'coupon_used',
  'reward_redeemed', 'point_earned',
  'visit_checkin', 'purchase'  -- 자리만 예약, 지금은 INSERT 안 함
))
```

**이중 쓰기 원칙** (결정 A):
- `game_complete` 기록은 `/api/games/play` 내에서 silent fail로 처리
- `coupon_used` 기록은 `/api/coupons/use`, `/api/coupons/verify` 내에서 silent fail로 처리

**전제 유지**: "게임 참여 = 매장 방문"이 항상 성립하지 않을 수 있다. visit_checkin을 enum에 예약해 향후 온라인 공유 시나리오를 대비한다.

---

### 3.3 방문 미션 = missions 신규 생성 (milestone_rules 대체)

**결정 E에 따른 확정**: milestone_rules는 DB에 없으므로 마이그레이션 없이 missions 신규 생성.

```sql
missions (기존 milestone_rules 역할 포함)
- id           uuid    primary key
- store_id     text    not null
- name         text    not null
- mission_type text    not null
  check (mission_type in ('visit_count', 'game_play_count', 'coupon_use_count'))
  -- 초기는 visit_count만 사용, 나머지는 enum 자리만 예약
- target_value integer not null
- reward_type  text    not null check (reward_type in ('coupon', 'point'))
- reward_value integer not null
- start_at     timestamptz
- end_at       timestamptz
- active       boolean not null default true

mission_progress (신규 — 결정 B에 의해 게임 완료 시 실시간 업데이트)
- id           uuid    primary key
- mission_id   uuid    references missions(id) on delete cascade
- store_id     text    not null
- kakao_user_id text   not null
- current_value integer not null default 0
- completed_at timestamptz  -- null이면 미완료
- unique(mission_id, store_id, kakao_user_id)
```

**업데이트 전략** (결정 B):
```
게임 완료 API에서:
1. 해당 store_id의 active 미션 목록 조회
2. mission_type = 'visit_count'인 미션의 mission_progress.current_value += 1
3. current_value >= target_value이면 completed_at = now() 기록
4. 완료된 미션이 있으면 보상(쿠폰 또는 포인트) 자동 지급
모두 silent fail — 미션 처리 실패가 게임 결과 반환을 막지 않는다.
```

### 3.4 고객 세그먼트 (부분채택)

**결정 C에 따른 업데이트 전략**: 게임 완료 시점에 해당 고객 1명만 즉시 재계산.

```sql
customer_loyalty (기존 테이블에 컬럼 추가)
+ segment              text  -- NEW / ACTIVE / AT_RISK / DORMANT / RETURNED
+ average_visit_interval integer  -- 단위: 일, 캐시값
```

**세그먼트 계산 규칙** (Rule Engine, AI 불필요):
```
방문 횟수 = 1회 → NEW (평균 방문주기 계산 건너뜀)

방문 횟수 ≥ 2회:
  개인 평균주기 = 총 방문 기간(일) / (방문 횟수 - 1)
  
  단, 방문 횟수 < 3이면 개인 평균주기 신뢰도 낮음 →
  store_settings.default_revisit_interval_days로 대체 (콜드스타트 fallback)
  
  최근 30일 내 재방문 있음 → ACTIVE
  마지막 방문 후 개인 평균주기 × 1.5 초과 → AT_RISK
  마지막 방문 후 개인 평균주기 × 3.0 초과 → DORMANT
  DORMANT 상태에서 지금 방문 → RETURNED (기록 후 ACTIVE로 전환)
```

**콜드스타트 fallback**: 방문 횟수 < 3이면 `store_settings.default_revisit_interval_days` 사용. 이 값도 없으면(NULL) 업종 기본값 14일을 하드코딩으로 사용. 방문 3회 이상이 되면 자동으로 개인 평균주기로 전환.

**등급(VIP) 관련**: 이번 v2.1에서는 세그먼트 저장까지만. 등급별 혜택은 4절 보류.

### 3.5 Win-back 로직 정교화 (기존 대체)

기존 12.2.2절을 3단계로 세분화. 결정 C와 동일한 fallback 규칙 적용.

```sql
churn_risk_alerts (기존 테이블에 컬럼 추가)
+ risk_level text  check (risk_level in ('interested', 'at_risk', 'dormant'))
```

**판정 기준** (결정 C의 fallback 동일 적용):
```
개인 평균주기 계산 가능 (방문 ≥ 3회):
  × 1.0~1.5배 경과 → interested (약한 보상)
  × 1.5~2.5배 경과 → at_risk (Win-back 캠페인)
  × 2.5배 초과    → dormant (강한 복귀 오퍼, 기간한정)

개인 평균주기 계산 불가 (방문 < 3회):
  store_settings.default_revisit_interval_days를 개인 평균주기 자리에 대입
  없으면 14일 하드코딩으로 대체
```

**churn_risk_alerts 업데이트 타이밍**: 세그먼트 재계산(결정 C)과 같은 시점 — 게임 완료 API에서 silent fail로 처리.

### 3.8 메시지 발송 원칙 (신규채택, 선행 필수)

**결정 D에 따른 동의 수집 방식**: 카카오 채널 친구추가 완료 = 동의.

```sql
message_consent
- store_id      text    not null
- kakao_user_id text    not null
- consented     boolean not null default false
- updated_at    timestamptz not null default now()
- primary key (store_id, kakao_user_id)

message_log
- id            uuid    primary key
- store_id      text    not null
- kakao_user_id text    not null
- message_type  text    not null
  check (message_type in (
    'expiry_reminder', 'winback_interested', 'winback_at_risk',
    'winback_dormant', 'mission_complete', 'coupon_issued'))
- sent_at       timestamptz not null default now()
```

**발송 규칙** (모든 발송 기능이 이 규칙을 통과해야 함):
```
발송 전 체크 순서:
1. message_consent 레코드 없음 → 발송 안 함 (카카오 미연동 기간 포함)
2. consented = false → 발송 안 함
3. 오늘 이미 발송 있음 → 발송 안 함 (하루 1회 제한)
4. 최근 7일 내 동일 매장 발송 3회 초과 → 발송 안 함
5. 동일 message_type 최근 발송일 < 재발송 허용 간격 → 발송 안 함
→ 위 5개 통과 시 발송 + message_log INSERT
```

**카카오 연동 전(mockLogin 기간)**: message_consent 레코드가 생성되지 않으므로 알림톡 발송 자체가 모두 차단됨. 의도된 동작.

### 3.9 확률형 게임 제품 원칙 (신규채택, 원칙 명문화)

기존 설계에서 암묵적으로 지켜온 원칙을 공식 반영한다.

- 게임을 반복 결제하게 만드는 구조로 설계하지 않는다 (본 서비스는 무료 참여 기반)
- 게임 결과(당첨/꽝)와 고객 등급·포인트를 불공정하게 연결하지 않는다
- 랜덤 게임 로직(4절)과 로열티 포인트 로직(13절)은 데이터 구조상 계속 분리 유지
- 향후 지역 확장 시 경품·쿠폰 프로모션 관련 법률 별도 검토

### 3.10 매출 기여 리포트 세분화 (부분채택)

기존 12.1.3절 + payment_logs(실측) 구조에 방문 단계별 매출 기여 추가.

```
게임 참여 → 첫 방문 전환 → 2회 방문 → 3회 방문 → VIP(세그먼트 연계)
각 단계별 고객 수 × 평균 결제액(실측 우선, 없으면 추정) = 단계별 매출 기여
```

기존 실측/추정 구분 배지 원칙 동일 적용.

## 7. 온라인 확장성 설계 원칙 (지금 할 일 아님 — 원칙 확인용)

| 원칙 | 현재 상태 |
|---|---|
| 매장(store) 위에 사업자(merchant) 계층을 얹을 수 있어야 함 | 나중에 merchant 테이블 + store.merchant_id만 달면 됨. 지금 작업 없음 |

| 고객 식별(kakao_user_id)과 채널/매장을 분리 | Satisfied — customer_loyalty가 (store_id, kakao_user_id) 복합키 |
| CRM 판단 로직과 발송 채널을 분리 | Satisfied — churn_risk_alerts(판단)와 message_log(발송)가 별도 |

**Cursor 실행 지시문 금지 규칙** (그대로 유지):
```
이번 세션에서는 merchant 테이블이나 온라인 채널 관련 테이블/필드를
새로 만들지 마라. 위 표의 "Satisfied" 항목들은 지금 구조를 유지하는

최상위 소유자라고 가정하는 로직을 피하고, store 자체가 상위 개체에
속할 수 있다는 가능성만 남겨두면 된다. 그 이상의 사전 작업은 하지 마라.
```
