# 룰렛 게임 마케팅 시스템 — 구조 설계도

**범위**: 오직 룰렛(스크래치카드 포함) 게임 마케팅 서비스 자체만 다룬다. 디자인 요소, 경쟁사 비교, Cursor 지시문은 포함하지 않는다. 목표는 "에러 없이 만들고, 완성 후에도 업데이트·확장·관리를 쉽고 빠르게 할 수 있는" 구조를 먼저 확정하는 것.

---

## 0. 전체 그림 한 줄

이 시스템은 **하나의 게임 엔진(룰렛/스크래치카드)을 중심으로, 그 위에 4단계 역할 계층(총관리자-대리점-프랜차이즈/광고주-매장)이 각자 다른 권한으로 접근하는 멀티테넌트 구조**다. 화면은 6개 군으로 나뉜다: 홍보사이트, 데모페이지, 광고주 관리자, 프랜차이즈 관리자, 대리점 관리자, 총관리자.

---

## 1. 역할 계층 구조 (누가 누구를 관리하는가)

```
                    ┌─────────────┐
                    │   총관리자   │  전체 시스템, 전 대리점/프랜차이즈/광고주 통합 관리
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │                         │
      ┌───────▼───────┐         ┌───────▼───────┐
      │   대리점(영업)  │         │  총관리자 직영   │  (대리점 없이 총관리자가 직접 계약한 광고주)
      │  지역/영업 단위  │         └───────┬───────┘
      └───────┬───────┘                 │
              │                         │
    ┌─────────┼─────────┐               │
    │                   │               │
┌───▼────┐       ┌──────▼──────┐        │
│ 광고주  │       │  프랜차이즈   │◄───────┘
│(단일매장)│       │ 본사(다지점)  │
└────────┘       └──────┬──────┘
                         │
                  ┌──────┼──────┐
                  │             │
              ┌───▼───┐    ┌────▼───┐
              │ 지점1  │    │  지점2  │  ...
              └───────┘    └────────┘
```

**핵심 판단 사항**:
- 광고주(단일 매장)와 프랜차이즈(본사+지점)는 서로 다른 계약 단위다. 프랜차이즈 본사는 지점들의 상위 계정으로, 지점 개별 캠페인도 볼 수 있지만 지점은 다른 지점 데이터를 볼 수 없다.
- 대리점은 자신이 영업해서 유치한 광고주/프랜차이즈만 관리한다. 대리점끼리는 서로의 고객 데이터를 볼 수 없다.
- 총관리자는 모든 계층을 가로질러 조회·개입 가능한 유일한 역할이다.

## 2. 데이터 모델 (핵심 엔티티와 관계)

| 엔티티 | 설명 | 소속 관계 |
|---|---|---|
| `Account` (계정) | 로그인 주체. `role` 필드로 구분(super_admin / agency / franchise_hq / franchise_branch / store_owner / staff) | 최상위 |
| `Agency` (대리점) | 영업 대리점 단위. 담당 지역, 수수료율 보유 | 총관리자 하위 |
| `Franchise` (프랜차이즈 본사) | 브랜드 단위, 지점 목록 보유 | 대리점 또는 총관리자 직영 하위 |
| `Store` (매장) | 실제 게임이 운영되는 최소 단위. 단독 광고주 매장이거나 프랜차이즈 지점 | 광고주/프랜차이즈 하위 |
| `Campaign` (캠페인) | 룰렛/스크래치카드 이벤트 1건. 기간, 상태(초안/운영중/종료) | Store 하위 |
| `Reward` (보상) | 캠페인에 속한 개별 경품. 확률·일한도·총한도·재고 | Campaign 하위 |
| `Participant` (참여자) | 게임 참여 기록. 전화번호(암호화), 참여일시, 당첨 결과 | Campaign 하위 |
| `Coupon` (쿠폰) | Participant에게 발급된 보상. 코드, 유효기간, 사용여부, 사용일시/처리자 | Participant 하위 |
| `Settlement` (정산) | 대리점 수수료, 프랜차이즈/광고주 이용료 청구 내역 | Agency/Store 하위 |
| `AuditLog` (감사로그) | 모든 계층의 주요 조작 기록(캠페인 생성/수정/쿠폰 강제처리 등) | 전역 |

**설계 원칙**: `Store`를 시스템의 진짜 최소 단위로 두고, `Campaign`/`Reward`/`Participant`/`Coupon`은 전부 `Store`에 종속시킨다. 광고주든 프랜차이즈 지점이든 게임 엔진 입장에서는 동일한 `Store`로 취급해야 나중에 "프랜차이즈 전용 기능"을 따로 하드코딩하지 않고 권한 레이어에서만 분기할 수 있다.

## 3. 권한 매트릭스 (RBAC)

| 기능 | 총관리자 | 대리점 | 프랜차이즈 본사 | 광고주(단일매장) | 매장 직원 |
|---|:---:|:---:|:---:|:---:|:---:|
| 전체 대리점/광고주 조회 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 소속 광고주/프랜차이즈 조회 | ✅ | ✅(자기 소속만) | — | — | — |
| 캠페인 생성/수정 | ✅ | ❌ (대행 세팅은 가능하되 광고주 승인 필요) | ✅(전 지점 배포) | ✅(자기 매장만) | ❌ |
| 지점별 성과 비교 | ✅ | ✅(자기 소속만) | ✅(자기 지점만) | ❌ | ❌ |
| 쿠폰 사용처리 | ✅ | ❌ | ✅ | ✅ | ✅ |
| 정산/수수료 확인 | ✅ | ✅(자기 몫만) | ✅(자기 청구만) | ✅(자기 청구만) | ❌ |
| 요금제/시스템 설정 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 감사로그 조회 | ✅ | ❌ | 자기 지점 범위만 | 자기 매장 범위만 | ❌ |

**이 표가 곧 API 인가(authorization) 설계의 기준 문서가 된다.** 화면을 만들기 전에 이 표부터 확정해야, 나중에 "이 버튼을 누가 눌러도 되는지" 화면마다 재논의하는 실수를 피할 수 있다.

## 4. 화면군별 사이트맵

### 4-1. 홍보 사이트 (공개, 로그인 불필요)
```
/ (홈)
/features (기능 소개)
/pricing (요금제)
/cases (도입 사례)
/agency-apply (대리점 지원 신청) ← 대리점 계층이 있으므로 반드시 필요
/franchise (프랜차이즈 전용 소개)
/contact (문의)
/demo (→ 데모페이지로 연결)
```

### 4-2. 데모 페이지 (로그인 없이 실제 게임 체험)
```
/demo → 가상 매장 선택 or 즉시 체험
   → 스크래치카드 체험 → 가상 보상 결과 → "지금 신청하기" CTA
```
**설계 원칙**: 데모 페이지는 반드시 실제 프로덕션 게임 엔진과 동일한 컴포넌트를 재사용해야 한다(별도 목업 제작 금지). 그래야 데모와 실제 서비스 간 UX 괴리가 생기지 않고, 게임 엔진 수정 시 데모도 자동으로 최신 상태를 유지한다.

### 4-3. 광고주 관리자 (단일 매장)
```
/admin/login
/admin/dashboard (전환 퍼널 요약)
/admin/campaigns (목록/생성/수정)
/admin/campaigns/:id (캠페인 상세, 실시간 참여 현황)
/admin/coupons (쿠폰 사용처리 화면 — 직원도 접근 가능한 별도 권한 레벨)
/admin/store-settings (매장 정보, QR 재발급)
/admin/billing (이용료/결제 내역)
```

### 4-4. 프랜차이즈 관리자 (본사+지점)
```
/franchise/dashboard (전 지점 통합 성과)
/franchise/branches (지점 목록, 지점별 드릴다운)
/franchise/campaigns (본사 일괄 배포 캠페인 관리)
/franchise/branches/:id/campaigns (지점 개별 캠페인 — 지점 접근 시 자기 지점만 보임)
/franchise/billing (지점별/통합 청구 내역)
```

### 4-5. 대리점(영업 대리점) 관리자
```
/agency/dashboard (소속 광고주 현황 요약, 이번 달 수수료)
/agency/clients (소속 광고주/프랜차이즈 목록, 신규 등록)
/agency/clients/:id (개별 고객 성과 조회 — 캠페인 수정 권한은 없음, 조회+대행 세팅 요청만)
/agency/settlement (수수료 정산 내역, 정산 주기 확인)
/agency/onboarding (신규 광고주 온보딩 가이드/체크리스트)
```

### 4-6. 총관리자
```
/super/dashboard (전체 매출, 전체 캠페인 수, 이상 징후 알림)
/super/agencies (대리점 관리, 수수료율 설정)
/super/franchises (프랜차이즈 관리)
/super/stores (전체 매장 조회, 직접 개입 필요 시 접근)
/super/settlements (전체 정산 현황)
/super/system-settings (요금제, 게임 유형 추가/제거, 기능 플래그)
/super/audit-log (전역 감사로그)
```

## 5. 확장성·유지보수 설계 원칙

이 항목이 "완성 후에도 업데이트·확장·관리를 쉽고 빠르게" 하기 위한 핵심이다.

### 5-1. 게임 엔진은 플러그인 구조로
룰렛과 스크래치카드는 물론, 향후 사다리타기 등을 추가할 수 있도록 게임 로직을 `GameEngine` 인터페이스로 추상화한다. `Campaign`은 `game_type` 필드만 가지고, 실제 확률 계산·애니메이션 트리거 로직은 게임 타입별 모듈로 분리한다. **새 게임 타입 추가 시 기존 코드를 수정하지 않고 모듈만 추가하는 구조**를 원칙으로 한다.

### 5-2. 권한 레이어를 데이터 레이어에서 강제
프론트엔드 화면 분기(이 버튼을 안 보이게 하는 것)만으로 권한을 제어하지 않는다. API/DB 레벨에서 "이 계정이 이 Store의 데이터를 볼 수 있는가"를 반드시 서버 측에서 재검증한다(예: Row Level Security 또는 서버 미들웨어에서 소속 관계 체크). 이래야 화면이 늘어나도 권한 누락 버그가 구조적으로 발생하지 않는다.

### 5-3. 스키마 검증을 프론트-백엔드 공유
캠페인/보상/쿠폰 데이터 구조를 하나의 스키마 정의(예: 공유 타입/검증 로직)로 관리해서, 관리자 화면 4종(광고주/프랜차이즈/대리점/총관리자)이 같은 데이터 구조를 다른 화면으로만 보여주도록 만든다. 화면마다 데이터 형태를 따로 정의하면 업데이트할 때마다 4곳을 각각 고쳐야 하는 실수가 반복된다.

### 5-4. 정산 로직은 별도 모듈로 격리
수수료·청구 계산은 캠페인/게임 로직과 완전히 분리된 모듈로 둔다. 정산 관련 버그는 실제 돈과 연결되므로, 이 부분만 별도로 테스트 커버리지를 두껍게 가져가고 다른 기능 변경이 정산 로직에 영향을 주지 않도록 격리한다.

### 5-5. 기능 플래그로 단계적 출시
프랜차이즈 관리자, 대리점 관리자처럼 초기엔 쓸 일이 적은 화면은 기능 플래그로 감싸서, MVP 단계에서는 꺼둔 채로 개발만 진행하고 필요한 시점에 계정 단위로 켤 수 있게 한다. 이러면 "언젠가 쓸 기능"을 미리 만들어두되 초기 운영 복잡도를 낮출 수 있다.

### 5-6. 감사로그를 처음부터 설계에 포함
누가 언제 어떤 캠페인을 수정했는지, 쿠폰을 누가 강제 처리했는지 등은 나중에 추가하기 어려운 항목이다. `AuditLog`는 데이터 모델 1단계 설계 때부터 포함시킨다(2장 참고).

### 5-7. 에러를 구조적으로 줄이는 3원칙
1. **타입 안정성 끝까지 유지**: 프론트-백엔드-DB까지 하나의 타입 체계로 연결해서, 필드 이름이나 타입이 어긋나는 실수를 컴파일 단계에서 잡는다.
2. **입력 검증은 항상 서버에서 최종 확인**: 관리자가 보상 확률 합계를 100%로 못 맞추거나, 확률이 음수가 되는 등의 오류는 화면에서만 막지 말고 서버에서도 반드시 재검증한다.
3. **중앙 에러 로깅**: 4개 관리자 화면 + 홍보사이트 + 데모페이지에서 발생하는 에러를 한 곳(예: Sentry 등 에러 모니터링 도구)으로 모아서, 어느 계층에서 문제가 자주 나는지 총관리자가 한눈에 볼 수 있게 한다.

## 6. 단계별 구축 순서 (구조 우선순위)

구조가 꼬이지 않으려면 만드는 순서 자체가 중요하다.

1. **데이터 모델 + 권한 매트릭스 확정** (2장, 3장) — 코드 작성 전 반드시 고정
2. **게임 엔진 코어** (Store/Campaign/Reward/Participant/Coupon의 최소 동작) — 관리자 화면 없이도 API/로직만으로 테스트 가능한 상태로 먼저 완성
3. **광고주 관리자 1개 화면군** — 가장 트래픽이 많은 계층부터 완성해 실제 파일럿 운영 시작
4. **데모 페이지** — 광고주 관리자와 게임 엔진이 안정되면, 같은 컴포넌트를 재사용해 빠르게 구축
5. **홍보 사이트** — 파일럿 성과 데이터가 쌓인 뒤 그 데이터를 콘텐츠로 반영해서 제작하면 더 설득력 있음
6. **대리점 관리자** — 하이브리드 판매 전략상 파일럿 이후 필요해지는 시점에 기능 플래그로 활성화
7. **프랜차이즈 관리자** — 실제 프랜차이즈 계약이 확정되는 시점에 맞춰 구축 (수요 확인 전 과잉 개발 방지)
8. **총관리자** — 1~7이 쌓이면서 필요한 조회·개입 기능을 그때그때 추가하는 방식으로, 처음부터 풀스펙으로 만들지 않음

## 7. 설계 완결성 체크리스트

- [ ] 모든 화면의 모든 액션이 3장 권한 매트릭스의 어느 셀에 해당하는지 매핑되는가
- [ ] `Store`를 최소 단위로 두고, 광고주/프랜차이즈 지점이 동일한 구조를 공유하는가
- [ ] 정산(Settlement) 로직이 게임 로직과 완전히 분리돼 있는가
- [ ] 새로운 게임 타입을 추가할 때 기존 코드 수정 없이 모듈 추가만으로 가능한 구조인가
- [ ] 감사로그가 처음부터 데이터 모델에 포함돼 있는가
- [ ] 데모 페이지가 별도 목업이 아니라 실제 게임 엔진 컴포넌트를 재사용하는가
- [ ] 권한 체크가 프론트엔드뿐 아니라 서버/DB 레벨에서도 강제되는가
- [ ] 6장의 구축 순서대로 진행 시, 각 단계가 이전 단계에 의존하지 않고 독립적으로 테스트 가능한가

## 8. 미확정 사항 후보

- **대리점 수수료 구조**: 정액제 vs 매장당 %, 초기엔 광고주 계약 건당 정액 수수료로 단순하게 시작하고, 데이터 쌓이면 성과 연동형으로 전환하는 방향 권장
- **프랜차이즈 vs 대리점 관리 매장의 경계**: 프랜차이즈 본사가 직접 총관리자와 계약하는 경우와, 대리점을 통해 프랜차이즈를 유치하는 경우 두 경로 모두 열어둘지 여부 — 2장 데이터 모델에서 `Franchise.agency_id`를 nullable로 설계해서 두 경로 모두 대응 가능하게 해둠
- **매장 직원 계정의 권한 세분화**: 초기엔 "쿠폰 사용처리만 가능"으로 단순하게 시작, 이후 필요 시 세분화
