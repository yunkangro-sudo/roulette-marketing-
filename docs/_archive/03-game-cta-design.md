## PART 1. 룰렛 게임 연동 마케팅 설계도

**목표**: 소비자는 최소 동작으로 참여·전환까지 끝내고, 광고주는 그 결과(재방문·팔로워·리뷰)를 실제로 얻는다. 모든 CTA는 "기술적으로 정말 클릭 1~2번에 끝나는지"를 먼저 검증한 것만 넣는다.

### 1-1. 소비자 참여-전환 플로우 (전체 그림)

```
[QR 스캔]
    ↓ (클릭 0 — 카메라 인식)
[랜딩 페이지 진입]
    ↓
[전화번호 입력 + 동의] ← 클릭 1회 (필드 입력 + 체크 1개)
    ↓
[게임 실행: 스크래치카드]
    ↓ (클릭 1회 — 긁기 제스처)
[결과 확인 화면]
    ↓
[전환 CTA 버튼 노출 — 아래 1-2 매트릭스 참고]
    ↓ (클릭 1~2회, 채널별 상이)
[쿠폰함 저장 완료]
```

**원칙**: 결과 화면에서 CTA 버튼은 **한 번에 1개만** 강조 노출한다. 여러 채널을 동시에 들이밀면 소비자가 아무것도 안 누르고 이탈한다. 업종·캠페인마다 "이번엔 어떤 CTA를 우선할지" 광고주가 관리자 화면에서 1개를 선택하도록 설계한다(복수 선택 시 우선순위 1개만 큰 버튼, 나머지는 하단에 작게).

### 1-2. CTA 채널별 기술 검증 매트릭스

| CTA | 필요 기술 | 소비자 클릭 수 | 전환 확인(측정) 가능 여부 | MVP 포함 |
|---|---|:---:|:---:|:---:|
| 카카오 채널 친구추가 | Kakao Channel 공식 SDK / `pf.kakao.com` 딥링크 | 2회 (CTA탭 → 카카오 내 추가확인탭) | 부분 가능 (콜백은 제한적, 클릭 수는 집계 가능) | ✅ 1순위 |
| 알림톡 재방문 쿠폰 자동발송 | 전화번호 기반 카카오 비즈메시지 API, 서버 트리거 | 0회 (소비자 행동 불필요, 서버가 자동 발송) | ✅ 완전 가능 (발송→클릭→방문 전 구간 추적) | ✅ 1순위 |
| 카카오 공유하기(바이럴) | Kakao Share 공식 SDK | 2~3회 (공유탭 → 친구선택 → 전송) | ✅ 가능 (공유 이벤트 수 집계) | ✅ 1순위 |
| 네이버 플레이스 저장 | `map.naver.com` 딥링크 (공식 API 없음) | 2회 (CTA탭 → 저장탭) | ❌ 불가 (클릭 수까지만 측정) | 🔶 2순위 |
| 당근마켓 단골 추가 | 비즈프로필 딥링크 (공식 API 없음) | 2회 (CTA탭 → 단골탭) | ❌ 불가 (클릭 수까지만 측정) | 🔶 2순위 |
| 리뷰 작성 즉시 리워드 | 자동 검증 API 없음 → 수동/반자동 확인 필요 | 3회 이상 (리뷰작성 → 인증수단 제출) | ⚠️ 자동 불가, 스크린샷 업로드 등 반자동 방식 필요 | 🔻 3순위 |
| 예약/웨이팅 연동 | 외부 예약 서비스(네이버예약 등) 딥링크 | 다수 (외부 서비스 소관) | ❌ 불가 (딥링크 클릭까지만) | 🔻 3순위 |

**정직하게 짚을 부분**: 당근·네이버·리뷰는 "클릭 2번으로 이동"까지는 기술적으로 문제없지만, **그 뒤 실제로 완료했는지는 시스템이 확인할 방법이 없다.** 이건 카카오도 마찬가지로 완벽하진 않다. 그래서 ROI 대시보드에는 "전환 완료율"이 아니라 "CTA 클릭률"까지만 정직하게 표시하고, 알림톡처럼 완전 추적 가능한 채널과 섞어서 과장하지 않는다.

### 1-3. 쿠폰·보상 콘텐츠 설계 원칙

- **보상명은 소비자가 매장에서 바로 쓸 수 있는 형태로**: "10% 할인" 같은 추상적 표현보다 "아메리카노 1,000원 할인"처럼 구체적 금액·품목으로 표기 (앞서 검토한 GameKick 카피 방식이 이 기준에 부합해서 참고할 만함)
- **쿠폰함 화면에 "사용 방법"을 1줄로 고정 노출**: "직원에게 이 화면 보여주세요" 같은 명확한 행동 지시. 소비자가 쿠폰을 받고도 어떻게 쓰는지 몰라 이탈하는 경우가 실제로 많음
- **유효기간은 재방문을 유도할 수 있는 기간으로 기본값 설정**: 너무 길면 긴급성이 없고, 너무 짧으면 재방문 확률 자체가 낮아짐 — 기본값 14~30일 권장, 광고주가 캠페인별로 조정 가능하게
- **직원용 처리 화면은 1탭 완료**: QR/코드 스캔 → 자동으로 "사용완료" 처리, 별도 확인창 최소화 (매장 혼잡 시간대에 직원이 여러 단계를 거치면 오히려 서비스 도입을 꺼리게 됨)

### 1-4. 마케팅 목적별 CTA 매핑

CTA는 전부 같은 목적이 아니다. 광고주가 "이번 캠페인의 목적"을 먼저 선택하면, 그에 맞는 CTA가 기본으로 추천되도록 설계한다.

| 마케팅 목적 | 우선 추천 CTA |
|---|---|
| 재방문 전환 (기존 고객 관리) | 알림톡 재방문 쿠폰, 카카오 채널 친구추가 |
| 신규 고객 유입 (확산) | 카카오 공유하기, 당근 단골(동네 노출) |
| 검색 노출 강화 | 네이버 플레이스 저장, 리뷰 작성 |
| 즉시 매출 전환 | 예약/웨이팅 연동 |

## PART 2. 우리가 그려야 할 설계도 — 전체 목록과 우선순위

지금까지 만든 것 + 앞으로 필요한 것을 정리하면 총 **8개**가 적정선이다. 전부 지금 만들 필요는 없고, 아래 우선순위대로 필요한 시점에 만드는 걸 권장한다.

| # | 설계도 | 상태 | 우선순위 | 비고 |
|---|---|---|---|---|
| 1 | 사업/마케팅 전략 기획서 | ✅ 완료 | - | 하이브리드 판매전략 문서 |
| 2 | 시스템 구조 설계도 | ✅ 완료 | - | 역할계층/데이터모델/화면군 |
| 3 | **게임 연동 마케팅 설계도** | ✅ 이번에 완료 | - | 본 문서 Part 1 |
| 4 | 데이터 모델 상세 설계도(ERD) | ⬜ 미작성 | 🔴 다음 순서 | 구조설계도의 개념도를 실제 테이블/필드 수준으로 구체화 — 코딩 착수 직전 필수 |
| 5 | API 명세 설계도 | ⬜ 미작성 | 🔴 다음 순서 | 엔드포인트·요청/응답 구조, 4번과 사실상 세트로 작성하는 게 효율적 |
| 6 | 정산/과금 설계도 | ⬜ 미작성 | 🟡 대리점 활성화 시점 | 지금 당장은 광고주 단일 매장 정산만 단순하게, 대리점 붙을 때 확장 |
| 7 | 개인정보·보안 설계도 | ⬜ 미작성 | 🔴 다음 순서 | 전화번호 수집·저장 서비스라 법적 리스크 있음, 코딩 착수 전 최소 원칙은 확정 필요 |
| 8 | 배포/운영 설계도 | ⬜ 미작성 | 🟢 파일럿 직전 | 모니터링·에러로그·백업 등, 실 서비스 오픈 직전에 확정해도 무방 |

**결론**: 지금 이 시점(코딩 착수 직전)에는 **4번, 5번, 7번을 다음 세트로 작성**하는 걸 권장한다. 이 3개가 확정돼야 실제 테이블/API를 만들 때 헤매지 않는다. 6번과 8번은 지금 만들어봐야 가정만 쌓이므로, 파일럿이 실제로 굴러가는 시점에 맞춰 작성하는 게 낫다.

## PART 3. Cursor 작업 구조와 순서

### 3-1. 폴더/모듈 구조 (설계도 → 코드 매핑)

```
/app
  /(public)          ← 홍보사이트 (설계도 3번의 사이트맵 반영)
  /demo               ← 데모페이지 (게임 엔진 컴포넌트 재사용)
  /play/[storeId]     ← 소비자 게임 참여 플로우 (본 문서 Part 1 핵심)
  /admin              ← 광고주 관리자
  /franchise          ← 프랜차이즈 관리자 (기능 플래그로 잠금)
  /agency             ← 대리점 관리자 (기능 플래그로 잠금)
  /super              ← 총관리자 (기능 플래그로 잠금)

/lib
  /game-engine        ← 게임 타입별 모듈 (roulette, scratch-card, ...)
  /cta-integrations    ← 채널별 CTA 연동 모듈 (kakao-channel, kakao-share, naver-place, danggeun, alrimtalk)
  /auth                ← 역할별 권한 체크 (3장 권한 매트릭스 그대로 구현)
  /schemas             ← 공유 타입/검증 스키마 (Campaign, Reward, Coupon 등)

/server (또는 API routes)
  /api/campaigns
  /api/participants
  /api/coupons
  /api/cta/kakao-channel   ← CTA 클릭 로그 기록
  /api/cta/alrimtalk        ← 알림톡 발송 트리거
```

**설계 원칙 연결**: `/lib/cta-integrations`를 채널별로 완전히 분리해두면, 나중에 CTA 채널을 추가/제거할 때(예: 배달앱 연동 추가) 다른 코드를 건드리지 않는다. 이건 시스템 구조 설계도 5장의 "플러그인 구조" 원칙을 CTA 레이어에도 동일하게 적용한 것이다.

### 3-2. 작업 순서 (착수 순서 그대로)

1. **`/lib/schemas` 먼저** — Campaign/Reward/Participant/Coupon 타입 정의부터 코드로 확정 (데이터 모델 설계도 4번을 이 단계에서 함께 구체화)
2. **`/lib/game-engine/scratch-card`** — 게임 로직만 순수 함수로 먼저 구현, UI 없이 콘솔/테스트로 확률·한도 로직 검증
3. **`/api/campaigns`, `/api/participants`, `/api/coupons`** — 기본 CRUD API (5번 API 명세 설계도가 이 단계의 기준 문서)
4. **`/play/[storeId]`** — 소비자 플로우 화면 연결 (Part 1의 플로우를 그대로 화면으로 구현)
5. **`/lib/cta-integrations/kakao-channel`, `kakao-share`** — MVP 1순위 CTA 두 개 먼저 연동
6. **`/admin`** — 광고주 관리자 (캠페인 생성, 대시보드, 쿠폰 처리)
7. **`/demo`** — 3~6단계에서 만든 컴포넌트 재사용해서 빠르게 구성
8. **`/lib/cta-integrations/alrimtalk`** — 서버 트리거형 CTA는 코어 플로우 안정화 이후 붙이는 게 안전 (발송 비용이 걸린 기능이라 테스트 신중히)
9. **`/(public)` 홍보사이트** — 파일럿 데이터가 나온 뒤 제작
10. **네이버·당근 CTA, 리뷰 리워드** — 2순위 CTA는 1순위가 안정화된 후 추가
11. **`/franchise`, `/agency`, `/super`** — 기능 플래그로 잠가둔 채 실제 필요 시점에 순서대로 개방

**이 순서를 따라야 하는 이유**: 게임 엔진과 소비자 플로우(1~4단계)가 안정되기 전에 관리자 화면이나 CTA 확장을 먼저 만들면, 코어 로직이 바뀔 때마다 여러 화면을 동시에 고쳐야 하는 상황이 생긴다. **코어부터 굳히고 바깥으로 확장하는 순서를 반드시 지킨다.**
