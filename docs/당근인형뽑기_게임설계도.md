# 당근 인형뽑기 게임 — 완전 설계도 (v2)

**문서 목적**: 룰렛을 대체하는 신규 게임("당근 인형뽑기")의 로직/UX/데이터 구조를 확정하여, 이후 디자인 및 Cursor 개발 착수에 바로 활용할 수 있는 실행 지시문 수준으로 정리한다.

**v2 변경사항**: 이벤트 다중 관리, 쿠폰 유효기간 분리, 캘린더 기반 기간 설정, 썸네일 업로드, 이벤트 상태머신 반영.

**v2.1 변경사항 (2026-08-09, 실제 구현 반영)**: 3~4절의 확률/재고 로직을 "확률(%) 직접입력 + 일/주/월 한도" 방식에서 **"수량 기반 자동계산"** 방식으로 전면 교체. 사장님이 %를 직접 입력하면 근거 없이 감으로 정하게 되고, 기간별 한도(tier_usage_counters)를 따로 관리하면 로직이 복잡해지는 문제가 있어 "총 준비 수량만 입력 → 시스템이 확률을 자동 계산"하는 방식으로 단순화했다. 상세 내용은 3.2·3.4·4절, 9절 데이터 모델 참고. 실제 구현: `lib/game-engine/probability.ts`(확률 계산+정규화), `lib/game-engine/prizeDraw.ts`(추첨+안전장치), `docs/migrations/004_quantity_based_prize_tiers.sql`, `005_normalize_prize_tier_probability.sql`.

## 0. 프로젝트 한 줄 정의

QR 스캔으로 진입한 손님이 손가락 드래그로 "당근 인형뽑기" 게임을 1회 플레이해 쿠폰을 즉시 받고, 고액 쿠폰은 당근마켓 단골 추가 확인을 거쳐야 매장에서 사용 가능하게 만드는 재방문 전환 게임 모듈. 매장(사장님)은 여러 개의 이벤트를 만들어 기간별로 운영할 수 있다.

## 1. 확정된 핵심 정책

| 항목 | 확정 내용 |
|---|---|
| 게임 참여 제한 | 매장당 하루 1회 (카카오 로그인 계정 기준, 1인 1일 1회) |

## 2. 손님 여정 전체 플로우 (End-to-End)

```
① QR 스캔 (매장 테이블/포스터 — 매장당 고정 QR 1개)
   ↓
② 서버가 "현재 활성(active) 상태인 이벤트"로 자동 라우팅
   - 진행중인 이벤트 없음 → "현재 진행중인 이벤트가 없어요" 안내 화면으로 종료
   - 진행중인 이벤트 있음 → 해당 이벤트의 썸네일/이벤트명으로 랜딩 페이지 구성
   ↓
③ 랜딩 페이지 진입 — 이벤트 썸네일 + 이벤트명 + [시작하기] 버튼
   ↓
④ 카카오 로그인 (재참여 제한 + 쿠폰 발송 겸용)
   - [카카오 로그인] 버튼 1탭 → 카카오 인증 동의 화면 → 완료 (SMS 인증번호 대기 없음)
   - 서버에서 (store_id + kakao_user_id + 오늘 날짜, 자정 KST 기준) 조합 하루 1회 체크
   - 이미 참여했으면 → "오늘은 이미 참여하셨어요! 내일 다시 도전해주세요" 안내 화면으로 즉시 분기
   - 로그인 직후, 아직 이 매장 카카오 채널 친구가 아니면 "이 매장 카카오 채널 추가하기" 1스텝 자연스럽게 노출
     (거부해도 게임 진행에는 지장 없음 — 선택사항)
   ↓
⑤ 게임 안내 화면 (최초 1회성, 스킵 가능)
   - "당근 인형을 손가락으로 움직이다 놓으면 뽑혀요!" 1줄 안내
   ↓
⑥ 게임 플레이 화면
   - 손가락으로 크레인 좌우 드래그 → 손 떼는 순간 자동 진행 (하강→집기→상승→배출, 약 2초)
   - 5초간 입력 없으면 "여기를 눌러도 뽑을 수 있어요" 탭 버튼 자동 노출 (고령층 폴백)
   ↓
⑦ 결과 공개 화면 ("짠!")
   - 당첨: 인형에 금액 라벨 + 컨페티 + "10,000원 쿠폰 당첨!"
   - 꽝: "다음 기회에!" + 격려 문구
   ↓
⑧ 결과별 분기
   [꽝]              → 포인트 적립 안내(⑦-1 참조, 13절) + 종료 화면 (카카오채널 추가 유도 배너)
   [1~2천원권 당첨]   → 즉시 발급 → 알림톡/문자로 쿠폰 코드 발송, 사용가능기간 함께 표시
   [1만원↑ 당첨]      → 예약 발급(pending_verify) → ⑨로 이동, 사용가능기간 함께 표시
   ↓
⑨ (1만원↑ 전용) 당근 단골 추가 유도 화면
   - "10,000원 쿠폰은 당근 단골 추가 후 매장에서 확인받고 사용할 수 있어요"
   - [당근에서 이 매장 단골 추가하기] 버튼 → 클릭 즉시 서버에 클릭 이벤트 기록(damgeun_click_logs) → 당근 비즈프로필 딥링크로 이동
   - 쿠폰 코드/QR + 사용가능기간("2026.08.10 ~ 2026.08.24") 항상 하단 노출
   ↓
⑩ 매장 방문 시 사용 (당일 또는 재방문 시, 사용가능기간 내 언제든)
   [1~2천원권] 직원이 쿠폰 QR 스캔 → 즉시 사용 처리 (기간 경과 시 자동 만료 안내)
   [1만원↑]    직원이 쿠폰 QR 스캔 → "당근 단골 확인" 화면 → [확인함]/[미확인 처리]
```

## 3. 이벤트(캠페인) 관리 구조 — 신규 핵심 설계

### 3.1 이벤트 상태머신

```
draft(임시저장) → scheduled(예약됨, 시작일 도래 전) → active(진행중)
                                                        ↓
                                              paused(일시중지) ⇄ active
                                                        ↓
                                                  ended(종료됨, 종료일 도래 또는 수동 종료)
```

- **paused**: 예산 초과·오류 등으로 급히 멈춰야 할 때 사용. 삭제와 달리 데이터·통계는 보존되고 재개(resume) 가능.
- **동시에 active 상태인 이벤트는 매장당 1개만 허용** (날짜 겹침 저장 시도 시 검증 오류로 저장 차단, 관리자가 순번을 명확히 인지하도록).
- ended 상태가 되어도 해당 이벤트로 이미 발급된 쿠폰은 자기 쿠폰 사용기간대로 별도로 유효.

### 3.2 이벤트 등록 화면 (관리자, 쉽고 간단하게)

| 필드 | 설명 |
|---|---|
| 이벤트명 | 텍스트 (예: "8월 여름맞이 당근뽑기") |
| 썸네일 이미지 | 업로드 (권장 비율/용량은 디자인 단계에서 확정, 미업로드 시 기본 이미지 자동 적용) |
| 이벤트 노출기간 | 캘린더에서 시작일 - 종료일 선택 (손님이 게임에 참여 가능한 기간) |
| 쿠폰 사용기간 | 아래 3.3 참조 |
| 경품 티어 | 금액, 총 준비 수량(total_quantity), 검증필요여부 — 여러 줄 추가 가능. **확률은 직접 입력하지 않는다** — (총 수량 ÷ 예상 참여자 수)로 자동계산되어 읽기전용으로 표시되며, 정규화 과정을 거쳐 항상 합계 100% (4.2절 참고) |
| 예상 일 참여자 수 | 관리자가 입력하는 추정값(`expected_daily_participants`) — 확률 자동계산의 콜드스타트용 기준치. 이벤트 노출기간(일수)과 곱해 "예상 참여자 수"를 산출한다 |
| [복제] 버튼 | 기존 이벤트 설정을 그대로 복사해 새 이벤트 생성 (날짜만 바꿔 반복 운영 시 편의) |
| [미리보기] 버튼 | 저장 전 손님 화면(랜딩+게임 인트로)을 관리자가 직접 확인 |

> **[v2.1 업데이트]** 원래 이 표에는 "일 한도/주 한도/월 한도" 필드가 있었으나, 실제 구현 단계에서 수량 기반 자동계산 방식으로 교체하면서 삭제했다. 이유: 일/주/월 단위로 따로 한도를 관리하려면 `tier_usage_counters` 같은 리셋 로직이 필요해 복잡해지고, 사장님 입장에서도 "이번 이벤트에 몇 개 준비했는지"(총 수량)가 "하루에 몇 개까지"(일 한도)보다 훨씬 직관적이다. 대신 `remaining_quantity`가 이벤트 전체 기간 동안 계속 차감되다가 0이 되면 자동으로 꽝 처리된다 (4.4절 참고).

### 3.3 쿠폰 사용기간 설정 옵션 (둘 중 택1, 이벤트별 설정)

- **옵션 A. 고정 날짜**: 캘린더로 "이 날짜까지 사용 가능" 직접 지정 (예: 이벤트 기간과 무관하게 8/31까지)
- **옵션 B. 발급일 기준 상대기간**: "발급일로부터 N일간 사용 가능" (예: 발급 후 14일) — 재방문 유도에 더 효과적, 기본 추천값으로 노출

쿠폰 화면과 계산대 검증 화면 양쪽에 **사용가능기간을 항상 텍스트로 표시** (예: "사용기간: 2026.08.10 ~ 2026.08.24").

### 3.4 한도 리셋 기준 — [v2.1: 폐기, 아래 대체 내용 참고]

원래 이 절은 일/주/월 한도의 자정 리셋 로직을 다뤘으나, 3.2절 업데이트대로 일/주/월 한도 개념 자체가 삭제되어 더 이상 적용되지 않는다.

**대체된 실제 동작**: `remaining_quantity`는 리셋되지 않고 이벤트 시작부터 종료(또는 소진)까지 계속 차감만 된다. 특정 티어가 소진(`remaining_quantity = 0`)되면 이후 그 티어는 다시 채워지지 않으며, 해당 이벤트가 끝날 때까지 뽑히지 않는다 (자동 꽝 전환 로직은 4.4절 참고).

### 3.5 진행 중 설정 변경 원칙

- 이벤트가 active 상태에서 경품 티어(총 수량)나 예상 참여자 수를 수정하면, **수정 시점에 확률을 재계산하고, 그 이후의 플레이부터만 새 설정 적용**. 이미 발급된 쿠폰과 과거 통계는 변경되지 않음 (사장님 문의/분쟁 방지를 위해 반드시 지켜야 할 원칙).

## 4. 확률 / 재고 로직 상세 — [v2.1: 수량 기반 자동계산으로 전면 교체됨]

### 4.1 경품 티어 구조 (이벤트에 종속, 예시값)

| 티어 | 금액 | 총 수량(`total_quantity`) | 검증 필요 | 계산된 확률(`computed_probability`, 자동) |
|---|---|---|---|---|
| 꽝 | 0원 | 관리자 설정 | - | 자동계산 (아래 4.2절) |
| 소액권 | 1,000~2,000원 | 관리자 설정 | 불필요 | 자동계산 |
| 고액권 | 10,000원 이상 | 관리자 설정 | 필요(당근 단골) | 자동계산 |

관리자는 확률(%)을 직접 입력하지 않는다. 각 티어의 `total_quantity`(이번 이벤트에 총 몇 개 준비했는지)만 입력하면, 시스템이 아래 4.2절 계산식으로 확률을 자동 산출해 읽기전용으로 보여준다.

### 4.2 확률 계산 로직 (이벤트 등록/수정 시점, 1회성 계산 후 고정)

**계산 시점**: 매 플레이마다 다시 계산하지 않는다. 이벤트를 등록하거나(또는 3.5절 원칙에 따라 진행중 이벤트를 관리자가 수정할 때) **딱 한 번 계산해서 `computed_probability` 컬럼에 저장**해두고, 이후 모든 추첨은 이 저장된 값을 가중치로 재사용한다.

```
1) 예상 참여자 수 = expected_daily_participants × 이벤트 노출기간 일수
                    (display_end_date - display_start_date)
2) 각 티어의 원시 확률 = tier.total_quantity ÷ 예상 참여자 수
3) 정규화(normalize): 모든 티어의 원시 확률을 합산한 뒤, 각 값을 그 합계로 나눠
   재조정한다 → 정규화된 값들의 합계는 항상 정확히 100%가 된다
   (구현: lib/game-engine/probability.ts의 normalizeProbabilities())
4) 정규화된 값을 prize_tiers.computed_probability에 저장
```

> 이유: `total_quantity ÷ 예상 참여자 수`를 티어별로 독립 계산만 하면 예상치가 부정확할 경우(예: 실제 참여자가 예상보다 적어 재고가 남는 경우) 합계가 100%에서 벗어난다(예: 91.7%). 정규화 단계가 있어야 "확률 합계는 항상 100%"라는 원칙(1절)이 지켜진다.

### 4.3 게임 결과 추첨 로직 (서버 사이드, 절대 원칙, `POST /api/games/play`)

1. 손님이 [뽑기 시작] 요청 시점에 **서버가 먼저 결과를 확정**한다 (클라이언트는 연출만 재생).
2. 추첨 알고리즘:
   ```
   1) 이벤트의 모든 prize_tiers를 조회
   2) 저장된 computed_probability를 가중치로 가중 랜덤 추첨
      (주의: remaining_quantity는 가중치로 쓰지 않는다 — 재고 자체를 가중치로 쓰면
       재고가 줄어들수록 확률이 흔들리는 버그가 생기기 때문에, 계산 시점에 고정된
       computed_probability만 가중치로 사용한다)
   3) 안전장치: 뽑힌 티어의 remaining_quantity가 이미 0이면(소진됨) → 꽝으로 강제 전환
      (구현: lib/game-engine/prizeDraw.ts의 applyStockSafetyNet())
   4) 최종 확정된 티어가 꽝이 아니면, 그 티어의 remaining_quantity를 1 차감
   ```
3. **동시 접속자 방어(DB 트랜잭션/row-level lock)는 이번 프로젝트 규모(로컬 소규모 사용자)에서는 불필요하다고 판단해 구현하지 않았다.** 단순 조회 → 차감 흐름이며, 동시 접속이 많아지는 시점에 Supabase RPC 원자적 update 도입을 재검토한다.

### 4.4 재고 소진 시 자동 강등 규칙

- `remaining_quantity`는 일/주/월 단위로 리셋되지 않고, 이벤트 시작부터 종료까지 계속 누적 차감된다 (3.4절 참고).
- 뽑힌 티어의 `remaining_quantity`가 0이면(이미 소진) 자동으로 꽝으로 전환한다 — 에러 노출 없이 매끄럽게 진행.
- 모든 유상 티어가 소진되면 결과적으로 항상 100% 꽝만 나온다.
- 관리자 대시보드의 "OO 쿠폰 소진" 실시간 알림 배너는 아직 관리자 화면 자체가 없어 미구현 (6단계 관리자 화면 작업 시 예정).

## 6. 쿠폰 발급 · 검증 로직

### 6.1 쿠폰 상태값 정의

```
issued        : 발급됨, 아직 미사용 (1~2천원권은 발급 즉시 이 상태)
pending_verify: 발급됨, 당근 단골확인 대기 (1만원↑ 전용)
used          : 매장에서 사용 완료
expired       : 쿠폰 사용기간 초과
unverified    : 검증 시도했으나 미확인 처리(사유 기록됨) — 사용기간 내 재시도 가능
```

### 6.2 상태 전이

- `pending_verify` → (직원이 [확인함] 클릭) → `used`
- `pending_verify` → (직원이 [미확인 처리] 클릭) → `unverified` (재방문 시 사용기간 내 재시도 가능)
- `issued` → (직원이 코드 스캔) → `used`
- 임의 상태 → (사용기간 경과 시 배치/스케줄러) → `expired`

### 6.3 직원용 검증 화면 요구사항

- 쿠폰 QR/코드 스캔 시 손님 정보(카카오 닉네임 일부, 당첨 금액, 당첨일시, **사용가능기간**) 표시
- 10,000원 이상권일 경우만 "당근 단골 확인" 버튼 세트 노출
- [확인함] 클릭 시 직원 계정 + 타임스탬프 기록 (감사로그)
- [미확인 처리] 시 사유 선택(앱없음/거부/기타) 필수
- 사용기간 경과 쿠폰은 스캔 시 "사용기간이 지난 쿠폰입니다" 즉시 안내, 사용 처리 버튼 비활성화

## 7. 예외 처리 케이스 표

| 상황 | 처리 방식 |
|---|---|
| 게임 도중 네트워크 끊김 | 서버가 이미 결과를 확정한 상태라면, 재접속 시 동일 세션 토큰으로 결과 화면부터 재개 |
| 손님이 결과 화면 보고 창을 닫음 | 알림톡/문자로 쿠폰 코드 발송했으므로 유실 없음 |
| 카카오 로그인 실패/거부 | 로그인 화면으로 재시도 안내, 3회 이상 실패 시 "잠시 후 다시 시도해주세요" + 고객센터 안내 |
| 드래그가 화면 밖으로 나감 | 드래그 가능 영역을 화면 경계로 클램핑 |
| 직원이 실수로 [확인함] 잘못 클릭 | 관리자(사장님) 권한으로만 취소 가능, 일반 직원 계정은 취소 불가 |
| 쿠폰 사용기간 만료 임박 | 만료 D-1 알림톡 자동 발송 (재방문 유도 효과 겸용) |
| 이벤트 active 중 특정 티어 재고 소진 | 자동 100% 꽝 처리, 에러 없이 매끄럽게 진행 (4.4절) |
| 이벤트 종료일 도래 | active → ended 자동 전환, 신규 참여 차단, 기발급 쿠폰은 자기 사용기간대로 유효 |
| 두 이벤트 날짜가 겹치게 저장 시도 | 저장 시점에 검증 오류로 차단, "이미 겹치는 기간에 진행중인 이벤트가 있어요" 안내 |
| 진행중 이벤트 확률 수정 | 수정 이후 플레이부터만 적용, 과거 데이터/통계 불변 |

## 8. 관리자(사장님) 화면 스펙

### 8.1 이벤트 관리 화면 (신규, 리스트형)

- 이벤트 카드 리스트: 썸네일 썸네일 + 이벤트명 + 상태뱃지(진행중/예약됨/종료됨/일시중지) + 기간
- 카드별 [수정] [일시중지/재개] [복제] [미리보기] [삭제(draft만 가능)] 액션
- [+ 새 이벤트 등록] 버튼 → 3.2 등록 폼으로 이동

### 8.2 이벤트 등록/수정 폼

- 3.2절 필드 그대로: 이벤트명, 썸네일 업로드, 노출기간(캘린더), 쿠폰 사용기간(고정일자/상대기간 택1, 캘린더), 경품 티어(총 수량 입력 → 확률 자동계산·합계 100% 표시), 예상 일 참여자 수
- 실시간 미리보기: "현재 설정 기준 기대 지급액(예상 방문자 수 입력 시 자동 계산)"

### 8.3 쿠폰 검증(계산대용) 화면

- 6.3절 참조 — 별도 태블릿/폰에서 바로 열리는 심플 뷰

### 8.4 대시보드

- 이벤트별 참여자 수, 티어별 당첨 분포, 재고 소진 현황(remaining_quantity 기준) (요약 카드)
- 쿠폰 사용률(issued 대비 used) — 재방문 전환 성과 지표 (요약 카드)
- unverified 사유별 통계 (요약 카드)

**쿠폰 현황 리스트 (심플 버전, 별도 화면 없이 대시보드 하단에 통합)**
- 표 1개: 날짜 / 손님(카카오 닉네임 일부 마스킹) / 당첨금액 / 상태 / 사용일시
- 상단 상태별 탭 클릭 필터만 제공: [전체] [발급됨] [사용완료] [미확인] [만료]
- 검색/정렬 등 추가 기능은 초기 버전에서 생략 — 사장님이 스크롤 한 번으로 오늘 상황 파악 가능한 수준까지만

**전환 퍼널 (당근 연동 성과 핵심 지표)**
- 당근은 클릭 발생 여부까지만 트래킹 가능하고 완료(단골추가) 여부는 API로 검증 불가하다는
  기술적 한계(당근마켓 리서치 문서 기준)를 반영해, 클릭 이벤트 자체를 퍼널 단계로 시각화:
  ```
  게임 참여 수 → 1만원↑ 당첨 수 → 당근 링크 클릭 수 → 실제 사용완료(검증) 수
  ```
- 오늘 기준 당근 링크 클릭 수를 단독 숫자 카드로도 노출 (damgeun_click_logs 카운트)
- 이 퍼널로 "당첨은 되는데 클릭을 안 함" vs "클릭은 하는데 매장 검증까지 안 이어짐" 같은
  구간별 이탈 지점을 사장님이 직관적으로 파악 가능

## 11. 실행 지시문 (Cursor 전달용 요약)

```
[기능명] 당근 인형뽑기 게임 + 이벤트 관리 모듈

[핵심 요구사항]
1. 손님 플로우: QR진입 → 활성이벤트 자동라우팅 → 카카오 로그인(하루1회, 자정KST리셋, 
   카카오 회원ID 기준) → (선택)카카오채널 추가 유도 → 드래그게임 → 결과공개 → 
   쿠폰발급(1~2천원 즉시 / 1만원↑ 단골확인 대기)
2. 게임 결과는 반드시 서버 사이드에서 사전 결정 (클라이언트 드래그는 연출 전용)
3. 이벤트는 상태머신으로 관리: draft/scheduled/active/paused/ended, 매장당 동시 active 1개 제한
4. 쿠폰 사용기간은 이벤트 노출기간과 분리된 별도 필드(고정일자 또는 발급일+N일), 
   손님 화면·계산대 화면 모두에 항상 표시
5. 경품 재고는 이벤트 전체 기간 기준 총 수량(total_quantity/remaining_quantity)으로 관리 (일/주/월 단위 리셋 없음), 소진 시 자동 100% 꽝 강등 (에러 노출 금지) — [v2.1] 확률은 (총수량÷예상참여자수) 자동계산 후 정규화하여 이벤트 등록 시점에 고정
6. 확률/한도 차감은 DB 트랜잭션으로 원자적 처리 (동시성 최우선 방어)
7. 진행중 이벤트 설정 변경은 변경 시점 이후 플레이부터만 적용 (과거 데이터 불변)
8. 관리자 화면: 이벤트 리스트(카드형, 복제/미리보기/일시중지 지원) + 등록폼(캘린더 기반 기간설정,
   썸네일 업로드, 확률 100% 자동검증) + 계산대 검증화면 + 대시보드(쿠폰 현황 상태별 탭 리스트 +
   당근 링크 클릭 전환 퍼널 포함)
9. 데이터 모델: 9절 스키마 참조 (events, prize_tiers, coupons, damgeun_click_logs 등 —
   [v2.1] tier_usage_counters는 삭제됨, prize_tiers가 total_quantity/remaining_quantity/
   computed_probability로 재고·확률을 통합 관리)

[기술 스택 참고]
- Next.js + Supabase (기존 프로젝트 아키텍처)
- 인증: 카카오 로그인 SDK (Kakao OAuth), kakao_user_id를 참여자 식별자로 사용
- 한도/재고 차감: Supabase RPC 함수로 원자적 update
- 캘린더 UI: 기간 선택(range picker) 컴포넌트
- 이미지 업로드: Supabase Storage
- 애니메이션: Framer Motion
```

## 12. 장기 리텐션 통계/리포트 기능 구현서 (구독 지속 전략)

**목표**: 이 게임마케팅을 6개월~1년 이상 지속 구독하게 만들려면, 단발성 성과가 아니라 **"시간이 지날수록 좋아진다"는 증거**와 **"우리가 알아서 매출을 만들어준다"는 체감**을 데이터로 계속 증명해야 한다. 아래는 이를 위한 기능을 구현 우선순위 기준 3단계(Phase)로 나눈 구현서.

### 12.0 3단계 로드맵 개요

| Phase | 시점 | 핵심 목표 | 포함 기능 |
|---|---|---|---|
| Phase 1 | 초기 MVP (이미 앞서 설계된 범위) | 기본 성과 가시화 | 전환퍼널, 쿠폰현황, 당근클릭수 — 1~9절에 기설계 |
| Phase 2 | 서비스 3~6개월차 | "좋아지고 있다"는 추세 증명 | 코호트 리텐션, 재방문주기 추이, 누적매출기여, 자동 월간 리포트 |
| Phase 3 | 서비스 6~12개월차 | "우리 없인 안 됐을 것"이라는 능동적 가치 | 트리거형 캠페인 자동화(날씨/번개이벤트), 이탈감지, AI 추천, 벤치마크, 에이전시 통합뷰 |

**설계 원칙**: Phase 1의 원시 데이터(game_events, coupons, damgeun_click_logs)만 잘 쌓아두면 Phase 2·3는 대부분 "집계 로직 + 화면"만 추가하는 문제로 축소된다. 즉 **Phase 1 데이터 모델이 향후 모든 리포트의 뼈대**이므로 지금부터 스키마 설계 시 아래 Phase 2·3 요구사항을 염두에 두고 필드를 넉넉히 잡아야 한다.

### 12.1 Phase 2 — "추세 증명" 기능 구현서 (3~6개월차 목표)

#### 12.1.1 코호트(Cohort) 리텐션 분석

**정의**: "이번 달 처음 게임에 참여한 손님 그룹이, 이후 몇 개월 동안 몇 %가 재방문(쿠폰 사용)했는가"

| 항목 | 스펙 |
|---|---|
| 코호트 기준 | kakao_user_id의 최초 game_events.played_at이 속한 월 |
| 추적 지표 | 코호트 발생 월 이후, 월별로 해당 유저의 coupons.status='used' 존재 여부 |
| 화면 표현 | 코호트 리텐션 테이블(행: 코호트월, 열: N개월 후 재방문율%) — SaaS 업계 표준 리텐션 매트릭스 형태 |
| 데이터 소스 | game_events + coupons (신규 테이블 불필요, 집계 쿼리로 처리) |

#### 12.1.2 재방문 주기 추적

| 항목 | 스펙 |
|---|---|
| 계산 방식 | 동일 kakao_user_id의 game_events.played_at 간격(일수)을 순차 계산 |
| 표현 | "평균 재방문 주기: 45일 → 20일" 같은 추이 라인그래프 (월별 평균 주기 변화) |
| 신규 테이블 | 불필요, game_events 원시데이터로 집계 가능 |

#### 12.1.3 누적 추정 매출 기여액

| 항목 | 스펙 |
|---|---|
| 계산식 | Σ(coupons.status='used'인 건수) × 매장 입력 "평균 객단가" |
| 필수 입력값 | store_settings 테이블에 `average_order_value`(사장님이 직접 입력하는 수동 필드) 신설 필요 |
| 표기 원칙 | 반드시 "추정치"임을 화면에 명시 (실 결제 데이터 연동 없음 — 이전 리포트 예시에서도 동일 원칙 적용) |
| 화면 표현 | 큰 숫자 1개 카드 ("지금까지 누적 추정 매출 기여: 2,124,000원") — 갱신 시점 설득력 핵심 요소 |

#### 12.1.4 자동 월간 리포트 발송

| 항목 | 스펙 |
|---|---|
| 발송 시점 | 매월 1일 자동 트리거 (cron job) |
| 발송 채널 | 카카오 알림톡 + 관리자 대시보드 내 PDF 다운로드 |
| 리포트 내용 | 11절 이전에 만든 "성과 리포트" 양식 그대로 자동 생성 (전월 데이터로 채움) |
| 신규 테이블 | `monthly_reports` (store_id, year_month, report_data(JSON), generated_at, sent_at) |
| 기술 참고 | PDF 생성은 서버사이드 렌더링 필요 (예: puppeteer 또는 react-pdf) — Cursor 개발 시 결정 |

#### 12.1.5 Phase 2 데이터 모델 추가분

```
store_settings (매장별 리포트 계산용 수동 입력값)
  - store_id
  - average_order_value          -- 사장님이 직접 입력, ROI 추정 계산용
  - updated_at

monthly_reports (자동 생성된 월간 리포트 아카이브)
  - id
  - store_id
  - year_month
  - report_data (JSON)
  - generated_at
  - sent_at
```

### 12.2 Phase 3 — "능동적 가치 증명" 기능 구현서 (6~12개월차 목표)

#### 12.2.1 이벤트 트리거형 캠페인 자동화 (날씨 연동 / 번개 이벤트)

**목적**: 시스템이 스스로 "지금이 이벤트 켤 타이밍"이라고 판단해서 매출 저조 구간을 메꿔주는 것 — 이게 "우리가 알아서 챙겨준다"는 체감을 만드는 핵심 기능.

| 캠페인 유형 | 트리거 조건 | 액션 |
|---|---|---|
| 비오는날 이벤트 | 외부 날씨 API(예: 기상청 API)에서 매장 위치 기준 강수 예보 감지 | 사장님에게 "내일 비 예보, 우천 이벤트 켤까요?" 알림톡 제안 → 승인 시 자동으로 한시적 이벤트(예: 당첨 확률 상향) 활성화 |
| 평일 번개 이벤트 | 과거 요일별/시간대별 참여 데이터에서 상대적으로 저조한 시간대 자동 감지(12.1.2의 시간대 패턴 데이터 활용) | "화요일 오후 2~4시가 평소 한산해요, 번개 이벤트 켤까요?" 제안 |

**중요 원칙**: 완전 자동 실행이 아니라 **"제안 → 사장님 승인" 구조**로 설계 (임의로 매장 확률/예산을 시스템이 바꾸면 신뢰 문제 발생 소지).

| 신규 테이블 | 스펙 |
|---|---|
| `campaign_triggers` | id, store_id, trigger_type(weather/slow_hour), suggested_at, approved(boolean), event_id(승인 시 생성된 임시 이벤트 연결) |
| `weather_snapshot` | date, store_id(또는 지역코드), condition(예: rain), fetched_at — 외부 API 캐싱용 |

**캠페인 성과 비교 리포트**: 캠페인 유형별로 "실행 전후 방문자수/전환율" 비교 테이블 — `campaign_triggers`와 `game_events`를 기간 조인해서 집계.

#### 12.2.2 이탈 위험 손님 자동 감지 + 리마인드

| 항목 | 스펙 |
|---|---|
| 감지 조건 | kakao_user_id별 마지막 game_events.played_at으로부터 "본인 평균 재방문 주기 × 1.5배" 이상 경과 시 이탈 위험군으로 분류 |
| 액션 | 카카오 알림톡으로 리마인드 쿠폰/이벤트 자동 발송 (예: "오랜만이에요! 다시 뽑으러 오세요") |
| 성과 측정 | 리마인드 발송 후 N일 이내 재참여 여부를 "회복률"로 리포트화 |
| 신규 테이블 | `churn_risk_alerts` (kakao_user_id, store_id, flagged_at, reminder_sent_at, recovered(boolean)) |

#### 12.2.3 AI 활용 제안 기능 (경량 버전 우선)

| 기능 | 설명 | 구현 난이도 |
|---|---|---|
| 다음 달 예상 참여자 수 | 과거 3개월 이동평균 기반 단순 예측 (AI 모델 없이도 시작 가능) | 낮음 |
| 경품 티어 최적화 제안 | "1만원권 비중 5%p↓ 시 예산 동일하게 참여자 X명 더 확보 가능" — 시뮬레이션 계산식으로 구현 (AI 불필요, 확률/예산 수식으로 충분) | 낮음~중간 |
| 다음 이벤트 추천 | 과거 캠페인 성과(12.2.1) 기반 규칙 기반 추천으로 시작, 추후 고도화 | 낮음 (초기), 중간(고도화) |

→ **설계 관점 조언**: "AI 추천"이라는 이름을 붙이되 초기엔 단순 통계 규칙으로 구현해도 충분히 체감 효과 있음. 진짜 ML 모델은 데이터가 충분히 쌓인 이후(1년+) 고려해도 늦지 않음.

#### 12.2.4 동종업종 벤치마크 (다매장 데이터 필요)

|---|---|

| 표현 | "귀 매장 재방문율 28% vs 동종업종 평균 19%" 익명화된 상대 비교 |
| 개인정보/신뢰 이슈 | 특정 매장이 식별되지 않도록 반드시 3개 매장 이상 집계된 카테고리에서만 노출 (표본 1~2개면 비교 자체 비활성화) |

### 12.3 정직한 제약사항 (구현서에 반드시 명시)

| 제약 | 설명 |
|---|---|
| 당근 "단골 수" 자체는 실측 불가 | 당근 API는 클릭만 트래킹 가능(기존 리서치 결론). 단골 순증 지표는 만들 수 없고, 대신 클릭수·검증완료수를 프록시 지표로 사용 |

| 벤치마크는 표본 수 확보 전까지 비활성 | 초기 매장 수가 적을 때는 동종업종 비교 기능 자체를 노출하지 않는 것이 안전 |

### 12.4 실행 지시문 추가분 (Cursor 전달용)

```
[Phase 2 우선 구현 대상 — 서비스 3~6개월차]
1. store_settings 테이블 신설 (average_order_value 등 사장님 수동입력 필드)
2. 코호트 리텐션 매트릭스: game_events + coupons 집계 쿼리로 구현 (신규 테이블 불필요)
3. 재방문 주기 추이: game_events.played_at 간격 집계 (신규 테이블 불필요)
4. 누적 추정 매출 기여 카드: coupons(used) 합계 × store_settings.average_order_value
5. monthly_reports 테이블 + 매월 1일 cron 트리거 + PDF 생성(react-pdf 등) + 카카오 알림톡 발송

[Phase 3 — 서비스 6~12개월차, 우선순위 낮음]
1. campaign_triggers, weather_snapshot, churn_risk_alerts 테이블 신설
2. 날씨/한산시간대 감지 → 사장님 승인 기반 임시 이벤트 자동 생성 워크플로우
3. 경품 티어 최적화 제안은 AI 없이 수식 기반 시뮬레이션으로 우선 구현
4. 동종업종 벤치마크는 표본 3개 매장 이상 확보 후 기능 활성화 (그 전엔 UI 자체 숨김)
5. 에이전시 통합 대시보드는 기존 역할(agency) 권한 체계에 조회 화면만 추가
```

## 13. 포인트 적립(로열티) 시스템 설계

**목적**: 게임 당첨(즉흥적 1회성 보상)과 완전히 분리된 **누적형 리텐션 트랙**을 추가한다. 방문할 때마다(게임 승패 무관) 포인트가 쌓이고, 임계값 이상 모이면 매장이 정한 리워드로 교환 가능. 여기에 방문 횟수 마일스톤 보너스까지 얹어 장기 재방문을 유도한다.

### 13.1 확정된 정책

| 항목 | 확정 내용 |
|---|---|
| 포인트 적립 조건 | QR 스캔 후 게임 1회 플레이 시, **당첨/꽝과 무관하게** 고정 포인트 적립 |
| 포인트 단위 | 원화(KRW) 가치로 직접 적립 (별도 "P" 환산 없이 직관적으로) |
| 적립 금액 | 매장(광고주)이 설정 (예: 회당 2,000원) |
| 사용 임계값 | 매장이 설정 (예: 5,000원 이상부터 사용 가능) — 대략 N회 방문해야 사용 가능해지는 구조 |
| 교환 방식 | 매장 자체 리워드 카탈로그 (사장님이 직접 등록, 예: "아메리카노 1잔 = 5,000P") |
| 방문 마일스톤 | 누적 방문 횟수 기준 별도 대형 리워드 지급 (예: 10회 방문 시 30,000원 특별쿠폰) — 포인트 잔액과 별개 트랙 |
| 적립 시점 제약 | 기존 하루 1회/매장 게임참여 제한과 자동 연동되므로 포인트도 자연히 하루 1회로 캡 (추가 방지로직 불필요) |

### 13.2 손님 여정에 추가되는 지점

```
(기존 ⑦ 결과 공개 화면 "짠!" 직후, 당첨여부와 무관하게 아래 삽입)
   ↓
⑦-1 포인트 적립 안내 (짧은 토스트/배너, 결과화면과 자연스럽게 연결)
   - "방문 포인트 2,000원 적립! (현재 잔액: 6,000원)"
   - 사용 임계값 도달 시: "포인트로 리워드 교환 가능해요!" 버튼 노출 → 리워드 카탈로그로 이동
   - 마일스톤 도달 시(예: 10회째 방문): "10번째 방문 축하드려요! 특별쿠폰 30,000원 증정" 별도 팝업
      → 해당 쿠폰은 금액 기준(10,000원 이상)에 따라 기존 6절 정책과 동일하게 
        당근 단골 검증 필요 여부 자동 판정
   ↓
(손님은 언제든 알림톡 링크로 "내 포인트" 웹뷰 접근 가능)
⑦-2 내 포인트 화면 (카카오 로그인 기반, 별도 앱설치 없이 웹뷰)
   - 현재 잔액 / 다음 방문까지 필요한 포인트 / 누적 방문 횟수
   - 매장 리워드 카탈로그 목록 (교환 가능/불가 상태 구분 표시)
   - [교환하기] 클릭 → 리워드 코드/QR 발급 (쿠폰과 동일한 issued→used 상태머신)
   ↓
⑦-3 매장 방문 시 리워드 사용 (기존 계산대 검증 화면 확장)
   - 직원이 리워드 QR 스캔 → 포인트 차감 처리 + 필요 시(고액 리워드) 당근 단골 검증 병행
```

### 13.3 데이터 모델 추가분

```
loyalty_settings (매장별 포인트 정책)
  - store_id
  - point_per_visit              -- 회당 적립 포인트(원 단위)
  - usage_threshold               -- 사용 가능 최소 잔액
  - point_expiry_days (nullable)  -- 매장이 관리자 화면에서 직접 설정 (13.5-1 확정). 
                                     --   null이면 무제한 보유, 값이 있으면 발급 후 N일 미사용 시 소멸
  - milestone_coupon_validity_days -- 마일스톤 보너스 쿠폰은 특정 이벤트에 종속되지 않으므로,
                                     --   매장 단위 기본 유효기간(발급일+N일)을 여기서 별도 설정 (coupons.valid_until 계산에 사용)

customer_loyalty (손님별 포인트/방문 누적 현황, 매장 단위)
  - store_id + kakao_user_id (복합 PK)
  - point_balance
  - visit_count
  - last_visit_at

point_ledger (적립/차감 전체 이력 — 감사로그 겸 통계 소스)
  - id
  - store_id
  - kakao_user_id
  - type (earn / redeem / milestone_bonus / expire)
  - amount
  - related_game_event_id (nullable)
  - related_reward_id (nullable)
  - created_at

milestone_rules (방문 마일스톤 규칙, 매장별 여러 개 등록 가능)
  - id
  - store_id
  - visit_count_threshold          -- 예: 10
  - reward_amount                  -- 예: 30000
  - requires_verification (boolean) -- amount 10,000원 이상 시 자동 true

reward_catalog (매장 리워드 상품, 사장님이 직접 등록)
  - id
  - store_id
  - name                           -- 예: "아메리카노 1잔"
  - point_cost                     -- 예: 5000
  - requires_verification (boolean) -- 사장님이 리워드 등록 시 직접 설정 (point_cost 자동추론 대신 명시적 설정,
                                     --   금액 무관 상품(예: 서비스 안주)도 있을 수 있어 명시값이 안전)
  - active (boolean)
  - stock (nullable, null=무제한)

rewards_issued (교환 발급된 리워드 — 쿠폰과 동일 상태머신 재사용)
  - id
  - reward_catalog_id
  - store_id
  - kakao_user_id
  - status (issued / used / expired)
  - issued_at / used_at
  - verified_by_staff_id (nullable)
```

| 대시보드 추가 지표 | 포인트 발급 총액 / 교환 총액(소진율) / 마일스톤 달성자 수 — 8.4절 대시보드에 카드 추가 |

### 13.5 미확정 사항 (다음 논의 필요)

| 항목 | 후보 |
|---|---|
| 고액 마일스톤 리워드의 검증 규칙 | 기본값은 기존 1만원 이상 쿠폰과 동일하게 당근 단골 검증 적용으로 가정 — 그대로 둘지 별도 규칙 둘지 확인 필요 |
| 포인트와 게임 확률의 연동 여부 | 지금은 완전히 분리된 트랙으로 설계했으나, 추후 "포인트 등급 높은 손님은 게임 확률 우대" 같은 결합도 Phase 3(12절) 확장으로 고려 가능 |

### 13.5-1 확정된 정책 (포인트 만료 / 재시도 제한)

| 항목 | 확정 내용 |
|---|---|
| 포인트 만료 정책 | **매장(광고주)이 직접 설정** — loyalty_settings.point_expiry_days를 관리자 화면에서 입력받는 필드로 노출 (미입력 시 기본값 null = 무제한 보유) |
| 미확인(unverified) 쿠폰 재시도 횟수 | **제한 없음** — 쿠폰 사용기간(valid_until) 내에서는 몇 번이든 재시도 가능. 유효기간 자체가 자연스러운 상한 역할을 하므로 별도 카운트 로직 불필요 |

### 13.6 실행 지시문 추가분

```
[포인트 시스템 구현 요구사항]
1. 게임 플레이 완료 시점(승패 무관)에 loyalty_settings.point_per_visit만큼 
   customer_loyalty.point_balance 증가 + point_ledger에 earn 기록 (트랜잭션 처리)
2. customer_loyalty.visit_count 동시 증가, milestone_rules와 비교해 도달 시 
   자동으로 rewards_issued 또는 coupons 생성(고액이면 6절 검증 로직 재사용)
3. "내 포인트" 웹뷰: 카카오 로그인 세션 기반 별도 페이지, 알림톡 링크로 접근
4. 리워드 교환: point_balance >= usage_threshold AND point_balance >= reward.point_cost 
   조건 충족 시에만 교환 버튼 활성화, 교환 시 원자적으로 포인트 차감 + rewards_issued 생성
5. 계산대 검증 화면(8.3절)에 리워드 QR 스캔 케이스 추가 — 쿠폰 검증 로직과 통합된 화면으로 확장
```

## 14. Cursor 개발 착수용 부록

**목적**: 1~13절이 "무엇을 만들지"였다면, 이 절은 "어떤 순서로, 어떤 API로, 어떤 환경으로 만들지"를 정한다. 디자인은 맨 마지막 단계이므로, 여기서는 순수 뼈대(로직+데이터+화면 골격)만 다룬다.

### 14.1 빌드 순서 (Phase)

한 번에 13절을 다 만들려 하지 말고 아래 순서로 진행한다. 각 단계가 끝나야 다음 단계가 의미를 가진다.

**원칙**: 가장 리스크가 큰(=처음 만들어보는, 실패 가능성이 있는) 부분을 가장 먼저 고립시켜 검증한다. 이 프로젝트에서 그건 랜딩/로그인이 아니라 **드래그 크레인 게임 인터랙션 자체**다. 그래서 게임 코어를 로그인·DB 없이 먼저 완전히 검증한 뒤, 나머지를 그 위에 얹는다.

| 순서 | 범위 | 참조 절 |
|---|---|---|
| 0 | 프로젝트 세팅 (Next.js+Supabase 초기화, 폴더구조, env) | 14.3~14.4절 |
| 1 | **게임 코어 단독 프로토타입** — 로그인/DB 없이 드래그+애니메이션+결과공개만, 결과는 클라이언트 임시 랜덤 | 3~4절 (로직은 나중, 인터랙션 먼저) |
| 2 | 랜딩 + 카카오 로그인 + 이벤트 자동 라우팅 (검증된 게임 컴포넌트를 붙임) | 2절, 5절 |
| 3 | 서버 사이드 확률 결정 + 한도 트랜잭션 (1단계의 클라이언트 랜덤을 서버 RPC로 교체) | 3~4절 |
| 4 | 쿠폰 발급/상태머신 (issued/pending_verify/used/expired/unverified) | 6절 |
| 5 | 계산대 검증 화면 (직원용) | 6.3절 |
| 6 | 관리자 이벤트 등록/관리 (CRUD, 상태머신, 캘린더 기간설정) | 3절, 8절 |
| 7 | 관리자 대시보드 (쿠폰현황 리스트 + 전환퍼널 + 당근클릭 트래킹) | 8.4절 |
| 8 | 포인트 적립/리워드 시스템 | 13절 |
| 9 | Phase 2 리포트 기능 (코호트, 재방문주기, 자동 월간 리포트) | 12.1절 — 위 0~8이 안정된 후 착수 |
| 10 | Phase 3 자동화 기능 (날씨트리거, 이탈감지, AI제안) | 12.2절 — 가장 마지막, 우선순위 낮음 |

**이유**: 1(게임 코어)이 가장 먼저인 건 실패 위험이 가장 큰 부분을 먼저 검증해야 나머지 작업이 헛수고가 안 되기 때문이다. 2~7이 없으면 사장님이 실제로 이벤트를 운영할 수 없고, 8(포인트)은 게임이 안정적으로 도는 다음에 얹는 게 맞고, 9~10(리포트/자동화)은 애초에 데이터가 쌓인 뒤에나 의미가 있으므로 제일 마지막이다.

### 14.2 API 엔드포인트 초안 (Cursor가 임의로 이름 짓지 않도록 고정)

```
[손님용]
POST   /api/auth/kakao/callback          카카오 로그인 콜백 처리, 세션 발급
GET    /api/events/active?store_id=      해당 매장의 현재 활성 이벤트 조회 (없으면 null)
POST   /api/games/play                   게임 플레이 요청 → 서버가 결과 확정 후 반환
                                          (game_event_id, result_tier, coupon 정보 포함)
GET    /api/loyalty/me?store_id=         내 포인트 잔액/방문횟수/리워드 카탈로그 조회
POST   /api/loyalty/redeem               포인트로 리워드 교환 요청
POST   /api/damgeun/click                당근 단골추가 링크 클릭 이벤트 기록

[직원/계산대용]
GET    /api/coupons/lookup?code=         쿠폰 코드로 상세 조회 (금액/상태/사용기간/검증필요여부)
POST   /api/coupons/verify               당근 단골 확인 처리 ([확인함]/[미확인 처리])
POST   /api/coupons/use                  쿠폰 사용 처리 (검증 불필요한 소액권)
POST   /api/rewards/use                  리워드 사용 처리

[관리자용]
POST   /api/admin/events                 이벤트 생성
PATCH  /api/admin/events/:id             이벤트 수정 (상태 전이 포함: pause/resume/end)
POST   /api/admin/events/:id/duplicate   이벤트 복제
GET    /api/admin/dashboard?store_id=    대시보드 집계 데이터 (퍼널, 쿠폰현황, 당근클릭수)
POST   /api/admin/loyalty-settings       포인트 정책 설정 (적립액/임계값/만료일수)
POST   /api/admin/reward-catalog         리워드 카탈로그 등록/수정
POST   /api/admin/milestone-rules        방문 마일스톤 규칙 등록/수정
```

### 14.5 Cursor에 전달할 최초 지시문 (그대로 사용)

```
이 설계도(당근인형뽑기_게임설계도.md) 전체를 읽고, 14.1절 순서대로 개발을 진행해줘.
```
